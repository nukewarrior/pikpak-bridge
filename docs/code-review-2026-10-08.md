## 1. 概要

项目的主要设计方向是合理的：PikPak 账号池自动选择与 aria2 下载目标显式选择相互独立；创建任务时快照下载目标；记录任务拥有的 PikPak 任务 ID、根文件 ID 和 aria2 GID；常规完成后只删除当前任务拥有的云端文件；SQLite 保存任务和事件以便重启恢复。

下一阶段最值得投入的不是扩展功能，而是提高**远端资源所有权、任务状态一致性、失败恢复、可观测性**的可靠性。

## 2. 已完成修复

### P0-01：取消与 PikPak 提交之间的竞态

**原问题**

取消接口可能先把任务写为 `CANCELLED`，而 PikPak 提交请求仍在执行。取消时数据库还没有远端任务 ID，清理操作无法定位它；随后提交返回 ID 时，普通任务保存又可能被终态保护拒绝，导致云端任务无人管理。

**PR #19 的修复**

- 取消先持久化为 `CANCELLING`，HTTP 返回 `202 Accepted`；不在请求线程直接执行远端清理。
- PikPak、aria2、收尾和取消 Worker 使用共享的**按任务互斥锁**，避免同一任务的外部副作用交叉执行。
- PikPak 提交成功后优先保存远端任务 ID，不再依赖后续普通状态写入是否成功。
- 对取消时仍在提交的任务，增加提交结果待确认标识；不允许旧 Worker 把 `CANCELLING` 恢复成运行状态。

**重要限制**

如果 PikPak 已接收提交，但进程在取得或保存其返回的 ID 前崩溃，或网络失败导致响应结果不确定，现有信息不足以安全确认到底创建了哪个远端任务。修复采取保守策略：保留 `CANCELLING` 和错误提示，**不声称已清理完成，也不按源链接随意认领其他云端任务**。建议后续设计专门的远端对账与人工处置流程。

关联代码：[取消 API](../internal/httpapi/server.go#L381-L398) · [PikPak 提交](../internal/worker/pikpak.go#L350-L440) · [取消状态存储](../internal/store/sqlite.go#L412-L475) · [互斥锁](../internal/worker/locks.go)。

### P0-02：取消失败后的清理自动恢复

**原问题**

取消后远端删除失败只被记录为错误，没有后续调度；重启后也不会接着清理。

**PR #19 的修复**

- 新增独立的取消清理 Worker，定期扫描 `CANCELLING`。
- 依次处理 aria2 下载、任务拥有的 PikPak 离线任务和云端根文件。
- 外部操作失败时保留状态和错误，持久化下一次执行时间，按有上限的指数退避重试。
- 程序重启后重新扫描待清理任务；所有资源确认清理后才进入 `CANCELLED`。
- aria2 HTTP 404 不简单等同于“该 GID 已不存在”，避免误判成功。
- 取消中且已知 ID 的 PikPak 远端任务继续计入部分活跃占用统计。

关联代码：[取消清理 Worker](../internal/worker/cancel.go) · [取消重试测试](../internal/worker/cancel_test.go) · [CI](../.github/workflows/ci.yml)。

**验证状态**：[PR #19 的 CI](https://github.com/nukewarrior/pikpak-bridge/actions/runs/37746301610) 已通过 `go test ./...`、`go test -race ./...`、`go vet ./...`、Go 编译及前端 JS 语法检查；**不等于已完成真实 PikPak/aria2 故障注入验证**。

## 3. 尚未修复的高优先级问题

### P0-03：Web/API 访问控制

**位置**：[HTTP 路由注册](../internal/httpapi/server.go#L66-L97)，以及 Docker 端口暴露相关配置。

**发现**：当前路由直接对外提供任务创建、取消、重试、配置管理等操作，没有统一身份验证/授权中间件。在局域网、反向代理错误配置或端口意外暴露时，能够访问服务的人可能操作任务、修改账号与 aria2 配置，或触发云端清理。

**建议**：
1. 至少加入强制认证，并明确首次初始化/常规 API 的保护边界。
2. 支持只监听受信任地址、反向代理鉴权或受信任网络访问；不要把“容器仅用于内网”当作永久的安全边界。
3. 对配置与任务破坏性操作增加必要的权限及审计记录；避免在日志或响应中暴露密钥。

**验收**：未认证访问任务、账号配置、取消/重试 API 应被拒绝；授权客户端正常操作；反向代理部署和初始化流程可测试。

### P1-01：手动重试丢失原有 PikPak 资源所有权

**位置**：[失败任务重试接口](../internal/httpapi/server.go#L400-L458)。

**发现**：`PIKPAK_FAILED` 分支调用 `ClearTransferState`，随后清空原账号 ID、远端任务 ID 和根文件 ID，再重新选择账号。若旧远端任务尚在运行，或取消失败/残留了云端文件，就可能丢失精确清理线索，并再次消耗离线下载次数/存储空间。

**建议**：重试之前先进行远端状态与所有权核对；需要清理的旧远端资源必须进入可恢复的清理阶段，并确认完成后才重置引用。不可确认时保持待人工核对状态，不直接清空远端 ID。

**验收**：卡死任务取消失败后手动重试、重试中断/重启、旧远端仍活跃等场景均不遗失所有权引用。

### P1-02：热更新可以“复用 ID、改变实体”

**位置**：[资源引用校验](../internal/httpapi/config.go#L226-L255) · [运行时配置应用](../internal/app/runtime.go#L84-L139)。

**发现**：目前校验主要保证仍被活跃任务引用的账号或 aria2 实例 ID 没有被删除、禁用；但同一个 ID 对应的 PikPak 用户名或 aria2 URL/实例实际身份可能被替换。已有任务持有旧 ID，却可能连接到另一个账户或 aria2 后端。

**建议**：对有活跃任务引用的资源，禁止修改关键身份字段；或把连接身份和配置版本快照到任务。校验引用与提交新配置之间也应有一致性保护。

**验收**：资源有活跃任务时不能以相同 ID 偷换账号身份/aria2 RPC 目标；普通无关配置仍可热更新。

### P1-03：账号并发额度统计仍有遗漏

**位置**：[远端已知任务集合](../internal/store/sqlite.go#L196-L218) · [活跃任务计数](../internal/store/sqlite.go#L220-L243) · [PikPak 账号状态同步](../internal/worker/pikpak.go)。

**发现**：PR #19 已将带远端 ID 的 `CANCELLING` 任务纳入部分活跃计数，但失败等其他状态下，已记录的远端任务仍可能运行，且已知 ID 集合会被从“外部任务”中排除，导致有效占用被低估。

**建议**：建立以 PikPak 远端状态为准的对账机制，将“本地失败但云端仍活跃”“取消待确认”“真正完成/不存在”等单独建模。定期重算账号占用，不只根据本地状态枚举推断。

**验收**：云端实际运行的任务不会因为本地进入失败态而释放并发名额。

### P1-04：传输完成校验不等于落盘验证

**位置**：[收尾校验](../internal/worker/finalizer.go#L114-L170)。

**发现**：当前检查 aria2 的 `completedLength == totalLength`，可选对比 PikPak 预期文件大小；尚未直接核验目标文件系统中的最终文件是否真实存在、大小是否吻合。aria2 报告完成后若磁盘文件被移动、截断或删除，远端源可能仍被清理。

**建议**：明确区分“RPC 元数据校验”和“落盘校验”；若服务能够访问下载目录，可额外 `stat` 文件（必要时校验散列）；不能访问时 UI 和日志应明确说明验证级别。只有满足配置的验证策略后才删除 PikPak 源文件。

**验收**：缺失、长度不匹配和权限不足都有明确结果，不能被误报为已完成实体校验。

### P1-05：配置文件的环境变量扩展范围过大

**位置**：[配置加载](../internal/config/config.go#L120-L135)。

**发现**：使用 `os.ExpandEnv` 对整份 YAML 文本展开。密码、令牌或目录里的字面量 `$NAME` 也可能被替换，导致重启后配置悄然变化。

**建议**：只对明确声明允许环境变量引用的字段解析，并采用约定清晰的占位语法；或者要求用户显式选择环境变量输入。增加密码、URL、路径包含 `$` 的测试。

**验收**：字面量 `$` 不被意外修改；缺少必填环境变量应报明确错误。

### P1-06：已完成但没有 RootFileID 的长期等待

**位置**：[PikPak 已完成状态](../internal/worker/pikpak.go#L424-L435) · [轮询分支](../internal/worker/pikpak.go#L460-L510)。

**发现**：服务端反复返回 `PhaseComplete`，却始终不提供 `RootFileID` 时，任务可能继续 `PIKPAK_RUNNING`、不断轮询；卡死检测主要位于运行态默认分支，无法可靠覆盖这个特殊情况。

**建议**：为“已完成但元数据缺失”设置单独超时与有限重试；超时后进入明确的可重试/待人工处理状态，并保留已有远端任务 ID。

**验收**：长时间缺少根 ID 不会无限轮询，也不会丢失后续查询、清理所需的引用。

### P1-07：卡死任务远端取消失败后的资源悬挂

**位置**：[PikPak 卡死处理](../internal/worker/pikpak.go#L495-L518)。

**发现**：连续无进展时会尝试取消远端任务，但即便取消失败，仍转为 `PIKPAK_FAILED`；用户再次手动重试可能进一步触发 P1-01。当前 PR #19 修复的“用户主动取消”流程，并未完整覆盖所有自动卡死/失败路径。

**建议**：将自动卡死的远端取消失败也交给统一的持久化清理/对账机制，避免失败终态掩盖仍在运行的云端资源。

## 4. 性能、体验与维护性改进

### P2-01：Worker 串行处理，存在队头阻塞

**位置**：[PikPak 主循环](../internal/worker/pikpak.go#L129-L149) · [aria2 主循环](../internal/worker/aria2.go#L88-L108) · [取消清理循环](../internal/worker/cancel.go#L62-L77)。

**发现**：每轮从数据库取出批量任务，再逐个执行可能阻塞的远端网络调用。单个账户或实例响应很慢时，会影响后续任务处理与取消恢复的及时性。

**建议**：先按任务加有界并发执行，同时对每个 PikPak 账号和 aria2 实例分别限制并发；保留任务互斥、幂等性和公平调度，避免简单增大协程数导致限流或重复副作用。

### P2-02：远端列表调用可能过于频繁

**位置**：[PikPak GetOfflineTask](../internal/pikpak/manager.go#L151-L171)。

**发现**：获取单个任务状态时会拉取该账号完整的 `OfflineTasks` 列表；任务数增大后同一轮可能重复拉取，增加 API 开销并可能触发限流。

**建议**：同账号每个轮询周期只拉取一次并构建 ID 索引；增加短 TTL 缓存和刷新失败退避，必要时根据 API 能力改为精确查询。

### P2-03：首页活跃任务可能显示不全

**位置**：[前端活跃任务查询](../internal/httpapi/web/app.js#L800-L815)。

**发现**：前端先请求最近 100 条任务，再在客户端筛选活跃状态。历史数据多时，较早创建、但仍活跃或卡住的任务可能不在返回的 100 条里，首页就不会显示。

**建议**：服务端提供按状态筛选及分页的查询，首页直接拉取活跃任务；任务历史单独分页。活跃数量由数据库独立统计。

### P2-04：同一资源全局唯一策略需要明确产品语义

**位置**：[SQLite 唯一约束](../internal/store/sqlite.go#L56-L80)。

**发现**：`source_key TEXT NOT NULL UNIQUE` 表示同一来源历史上只能创建一次，即使任务完成或失败。它可以避免某些重复任务，但也阻止用户有意重新下载或下载到另一个目标。

**建议**：先确定期望规则：仅阻止活跃任务重复？允许已完成任务重新创建？不同目标是否允许同源？再选择部分唯一索引或“复用任务/重新下载”操作。**放宽去重前必须确认远端所有权与清理机制不会因此冲突。**

### P2-05：健康检查与运维可观测性

**位置**：[HTTP 健康路由](../internal/httpapi/server.go#L79-L102) 及各 Worker。

**建议**：把存活检查和就绪检查分开，补充数据库可写性、Worker 最后成功扫描时间、取消清理积压量/最老积压时长、重试失败次数、远端任务已知与未知数量、账号配额与实例故障情况；不要因外部服务短暂不可用而直接判定主进程应重启。

### P2-06：故障注入与持续测试

**现状**：PR #19 已加入取消并发、清理失败、重启恢复等回归测试，CI 增加 `go test -race ./...`。

**仍建议补充**：

- PikPak 提交成功、数据库写入前强制退出；同时核对未知结果的人工处置路径。
- aria2 已接收下载，但保存 GID 前退出；确认不会重复提交/覆盖文件。
- 云端删除部分成功、随后超时/连接中断；验证多次执行仍安全。
- 下载完成、云端清理前重启；确认不会遗失云端资源或重复下载。
- PikPak 账号不可用/配额耗尽、多账号限流；验证任务公平性与回退。
- 卡死自动取消失败→手动重试→重启；验证远端所有权不丢失。
- 同一任务同时被轮询、取消、收尾及配置更新命中；用竞态检测验证。
- `PhaseComplete` 长期缺少 `RootFileID`，以及 aria2 磁盘空间不足、下载失败和局部完成场景。

## 5. 推荐实施顺序

| 阶段 | 工作 | 预期收益 |
| --- | --- | --- |
| 第一阶段 | **P0-03 认证与部署访问控制** | 防止未经授权操作或误删 |
| 第二阶段 | **P1-01 / P1-07 / P1-03 统一远端对账、失败清理及重试所有权** | 避免孤儿云下载、重复配额消耗及占用误判 |
| 第三阶段 | **P1-02 配置身份约束、P1-05 环境变量安全** | 消除热更新/重启后连接到错误账号或实例的风险 |
| 第四阶段 | **P1-04 落盘校验、P1-06 根文件 ID 超时** | 防止未验证数据被提前清理，减少永久卡住 |
| 第五阶段 | **P2 并发调度、轮询批处理、服务端分页、可观测性与故障注入** | 改善吞吐、用户体验与长期维护效率 |

### 实施约束

- **代码质量和正确性优先**；任务状态转换必须具有明确的所有权、不变量和恢复策略。
- 用户当前处于开发阶段，可按需清空 SQLite 任务数据库，不必为旧开发数据设计复杂迁移；但需明确区分数据库与保存登录信息的 `sessions` 目录。
- 保持已明确的产品规则：PikPak 账号自动分配，aria2 目标由用户显式选择；保留目录层级；不随意删除其他任务的云端文件。
- 新增远端副作用前优先回答：请求接受但响应丢失怎么办？部分成功如何回滚/重试？重复执行是否幂等？重启后如何找回所有权？

## 6. 总结

PR #19 已显著改善**用户主动取消**的状态一致性和清理恢复，但还不能将所有“远端资源失去管理”风险视作彻底解决：**失败任务手动重试、自动卡死取消、跨账号远端对账、提交结果未知**仍需要整体治理。下一个可靠性里程碑应该是形成覆盖所有异常状态的“远端任务拥有权 + 可恢复清理 + 资源对账”闭环；同时尽快补齐访问认证。
